# 个人音乐管理平台技术实现方案

## 1. 技术选型

- 后端语言与框架：Python + FastAPI + Uvicorn
- 配置：`pydantic-settings`（`.env`），含数据库、S3、`DEFAULT_FORMAT_PRIORITY`
- 关系数据库：SQLite（默认）；支持 PostgreSQL / MySQL（连接串与方言由 `DATABASE_URL` 决定）
- 对象存储：S3 协议（AWS S3 / MinIO），存音频对象；**封面桶**在配置中存在，业务以音频为主
- ORM 与结构补齐：SQLAlchemy 2.x；**无 Alembic**，启动时 `ensure_schema` + `create_all` 做增量列/表与一次性迁移标记
- 元数据解析：mutagen
- 前端：原生 HTML + JavaScript + CSS（`app/static/index.html`、`admin.html` 等）
- 时区：应用层北京时间（SQLite）；PostgreSQL/MySQL 可在连接时设 `database_timezone`（如 `Asia/Shanghai`）
- 测试：可自行引入 pytest / httpx 等（当前 `requirements.txt` 以运行时依赖为主）

---

## 2. 架构设计

### 2.1 分层结构

1) API 层
- 歌曲（列表/详情/更新/删除/播放/按歌下载/加挂文件）、歌单、艺人（`/people`）、标签、语言、**风格**
- 文件行：`GET/PATCH/DELETE /song-files/{id}`（流式、下载、重命名展示名、删存储）
- 后台：`POST /admin/import-directory`（multipart）、`/admin/scan-progress`、**批量筛选选项** `/admin/filter-options`、**批量下载**、**合并重复/合并所选**、**按元数据同步对象键**
- 库扫描：`POST /libraries/scan`（服务端路径，写 `scan_jobs`）

2) Service 层
- 入库：`ingest_file`、目录扫描；元数据提取；对象存储上传与路径规则（见 §4）
- 同曲合并：`song_merge`（启动去重、管理端合并所选）；**`relocate_song_files_storage`** 按当前元数据调整 `object_key`
- 播放/列表：`choose_best_file` 等与 `DEFAULT_FORMAT_PRIORITY` 协调

3) Repository 层
- SQLAlchemy `Session` 访问数据库

4) Storage 层
- `app/storage.py`：boto3 封装 S3，预签名/上传/复制/删除等

### 2.2 核心原则

- 数据库不存音频二进制，只存元数据与 **`object_key`**
- 音频对象统一在 S3/MinIO；通过 **`song_file_id`** 或 **`song_id` + 格式选择** 访问，不对外暴露真实桶路径
- 元数据保存、文件重命名、合并、批量更新等可能触发桶内 **copy + 删旧键** 的路径调整（与 README 一致）
- 静态资源由服务端 `FileResponse`/`StaticFiles` 提供；缓存策略可按部署加版本 query

## 3. 数据模型设计（支持同曲多格式并存 + 艺人多角色）

> 以下与代码 [app/models.py](app/models.py)（SQLAlchemy 2.x）一致。SQLite 中整数/字符串/布尔/时间分别映射为 INTEGER、VARCHAR/TEXT、BOOLEAN（或 0/1）、DATETIME；PostgreSQL/MySQL 由方言映射。

### 3.1 主实体与关系概要

- **Song**：逻辑歌曲（一条业务上的「歌」）
- **SongFile**：该歌在对象存储中的物理文件行（可多格式多行）
- **Artist**：艺人；`types` 描述角色（如歌手/作词/作曲）
- **Album**：专辑；`songs.album_id` 指向专辑
- **Language / Genre / Tag**：主数据表；歌曲通过关联表支持多语言、多风格、多标签
- **SongLeadArtist / SongChorusArtist / SongLyricistArtist / SongComposerArtist**：歌曲与艺人的多对多（**原唱/主唱**、合唱、作词、作曲）；当前**产品界面**侧重原唱、作词、作曲，合唱数据层可保留、界面较少展示
- **关系**：Song 1:N SongFile；Song 与 Artist/Language/Genre/Tag 均为 N:M（关联表）；`songs` 上 `artist_id`、`chorus_artist_id`、`language_id`、`genre_id` 与关联表并存，用于兼容筛选及「首项」同步

### 3.3 关键约束与说明

- `song_files.song_id`：同一首歌可对应多行（多格式并存）。
- `song_files.object_key`：**全局唯一**；同一内容可因合并等存在多行不同 `object_key`（历史上曾调整 `(sha256, file_size)` 全局唯一策略，以当前模型为准）。
- `artists.types`：多角色由应用层维护，非独立关联表。
- `songs` 上单列 `language_id` / `genre_id` / `artist_id` / `chorus_artist_id` 与多对多表**并存**：列表筛选、接口兼容与「首项」同步逻辑依赖这些列。
- 外键删除策略以实现为准（部分场景使用 `passive_deletes` 等避免误级联）。

## 4. 对象存储方案

### 4.1 桶规划

- music-files：音频文件
- music-covers：封面图片

### 4.2 对象键规范（与实现一致）

- **音频**：`music/{原唱1&原唱2}/…/{歌曲名}/…/{文件名}.{格式}`（路径段清洗非法字符；冲突时自动加 `_` + 哈希后缀；**以 README 与 `relocate` 实现为准**）
- **封面桶**：配置项 `s3_bucket_covers` 预留；封面键规范若启用需与实现同步

### 4.3 上传与入库要点

1. 浏览器上传或扫盘得到本地/临时文件路径
2. 计算 `sha256` 等；同内容已存在可跳过；**同一逻辑歌**（同标题 + 同主艺人等规则）可只追加 `SongFile` 而不新建 `Song`
3. 上传到对象存储，落库 `song_files`（`object_key` 全局唯一）

### 4.4 下载/播放策略

- 播放：`GET /song-files/{song_file_id}/stream`，支持 Range
- 按歌下载：`GET /songs/{song_id}/download?formats=...`（多种格式时 ZIP）；`GET /song-files/{id}/download` 单曲文件行
- 后台批量：`POST /admin/songs/batch-download`（多首多格式 ZIP）
- 同源代理，减少浏览器拦截；大文件注意超时与反向代理缓冲

## 5. 扫描与入库流程

**路径 A：后台浏览器导入（常用）**

1. 用户选择**目录**（`webkitRelativePath`）或**多文件**，`POST /admin/import-directory`（`multipart/form-data`，字段 `files`）
2. 服务端写入临时文件并逐文件 `ingest_file`；全局内存 `scan_progress` 记录进度（`GET /admin/scan-progress`）
3. 提取 mutagen 元数据，建/更新 `Song`、`SongFile`，上传对象存储
4. 返回 `ScanResult`（含 `skipped_details` 等），前端可弹窗展示跳过原因

**路径 B：服务端目录扫描**

1. `POST /libraries/scan`，body 可选目录（默认 `import_root`）
2. `scan_directory` 递归文件并入库，写入 **`scan_jobs`** 行

**其他**：启动时若配置了迁移标记，可能对历史重复 `Song` 执行**自动合并**（见 README「重复歌曲合并」）；管理端另提供 `POST /admin/merge-duplicate-songs`、`POST /admin/songs/merge-selected`

## 6. 播放与下载设计

### 6.1 默认播放优先级（可配置）

1. FLAC/ALAC（若浏览器可播）
2. AAC/M4A
3. MP3
4. 其他可播放格式

### 6.2 业务行为

- 列表/播放默认按策略选用最优 `SongFile`；前后台均可**指定格式**（query、下拉或批量 body）
- `GET /songs/{song_id}/download`：支持 `formats` 多值；多文件时响应 **ZIP**
- `POST /admin/songs/batch-download`：body `song_ids`、`formats`；多文件 **ZIP**

## 7. API 设计（与 `app/main.py` 路由对齐）

### 7.1 健康与库信息

- `GET /health`
- `GET /library/stats`：歌曲数、歌单数等

### 7.2 歌曲与文件

- `GET /songs`：歌曲列表（`offset`、`limit`）
  - `keyword`：标题、原唱、合唱、专辑、作词、作曲等（实现见 `main.py`）
  - 筛选：`formats`、`lead_artists`、`chorus_artists`、`lyricists`、`composers`、`tag_ids`、`languages`、`genre_ids`、`bitrates`、`sample_rates` 等
  - **`tag_ids`（多值）**：歌曲的标签名集合与**任一**所选标签名有交集即通过（**OR**）；仅当查询参数中的 id 至少能解析出一条有效 `Tag` 时才应用该条件，若全部无效则**不按标签过滤**（与前台「多选标签 = 或」一致；迭代说明见 **`iterations/20260401.md`**）
  - 各筛选维度之间为 **AND**（与其它 query 组合方式以 `main.py` `list_songs` 为准）
  - `sort_by` / `sort_order`：如 `title`、`created_at`、`duration_ms`、`release_date`、`album`、`language`、`genre`、`film_tv`、`updated_at` 等
  - 响应体为 `SongOut` 列表（含 `file_variants`、`film_tv`、`updated_at` 等）

- `GET /songs/{song_id}`：`SongDetailOut` + `files`
- `PUT /songs/{song_id}`：更新元数据（可多选语言/风格/艺人角色等）；可能触发 **`relocate_song_files_storage`**
- `DELETE /songs/{song_id}`：删除歌曲及关联
- `PUT /songs/bulk`：批量更新（如艺人、专辑、标签）

- `GET /songs/{song_id}/play`：返回推荐 file 与 stream/download URL
- `GET /songs/{song_id}/download`：按歌下载；多格式 ZIP
- `POST /songs/{song_id}/files`：`multipart/form-data`，字段 `file`，追加一条 `SongFile`

- `GET /song-files/{song_file_id}/stream`：Range 流式播放
- `GET /song-files/{song_file_id}/download`：单文件下载
- `PATCH /song-files/{song_file_id}`：更新 `original_filename`（扩展名与格式一致）；可触发对象键迁移
- `DELETE /song-files/{song_file_id}`：删除存储中的对象与数据库行

### 7.3 歌单

- `GET /playlists`、`POST /playlists`、`PUT /playlists/{playlist_id}`、`DELETE /playlists/{playlist_id}`
- `PUT /playlists-reorder`：歌单列表排序
- `GET /playlists/{playlist_id}`：`PlaylistDetailOut`（内含 `songs`）；前台可在客户端对 `songs` 再应用关键词与格式/标签/语言筛选，其中**多选标签为 OR**（与 `GET /songs` 一致，见 **`iterations/20260401.md`**）
- `POST /playlists/{playlist_id}/items`：添加一首歌曲
- `DELETE /playlists/{playlist_id}/items/{song_id}`：移除

### 7.4 艺人 / 标签 / 语言 / 风格

- `GET/POST /people`，`PUT/DELETE /people/{person_id}`（响应 `PersonOut` / `types`）
- `GET/POST /tags`，`PUT/DELETE /tags/{tag_id}`
- `GET/POST /languages`，`PUT/DELETE /languages/{language_id}`
- `GET/POST /genres`，`PUT/DELETE /genres/{genre_id}`

### 7.5 后台运维与扫描

- `GET /admin/filter-options`：管理端筛选项（艺人、风格、标签等）
- `GET /admin/scan-progress`、`POST /admin/scan-progress/reset`：导入进度（内存字典，非 `scan_jobs`）
- `POST /admin/import-directory`：`multipart`，浏览器目录/多文件导入
- `POST /libraries/scan`：`ScanRequest`，服务端路径扫描并写 **`scan_jobs`**
- `POST /admin/songs/batch-download`：批量 ZIP
- `POST /admin/merge-duplicate-songs`：重复 `Song` 合并（与启动迁移逻辑同类）
- `POST /admin/songs/merge-selected`：body `song_ids`、`master_song_id`；**仅收并文件**，不改主曲元数据
- `POST /admin/songs/{song_id}/relocate-storage`：按当前元数据同步该歌对象键

### 7.6 静态页面

- `GET /` → `index.html`；`GET /admin` → `admin.html`；`/static/*` 静态资源
- 音乐列表条件筛选（`frontend.js` / `admin.js`）：隐藏原生 `<select multiple>`，由 **searchable-select**（搜索框 + 选项区）渲染；多选为复选框行。管理端行内（含文案区）切换勾选时优先通过 **`input.click()`** 走原生切换，以可靠触发 **`change`** 并回写 `<option selected>`、再向 `<select>` 派发 **`change`** 拉取列表（避免仅改 `checked` 属性时部分 UA 不触发 `change`）。样式与交互细节见 **`iterations/20260401.md`**。

## 8. Schema 迁移（ensure_schema）

在系统启动时自动执行数据库迁移（见 `app/main.py` 中 `ensure_schema` 与启动逻辑）：

1. 确保表存在：`languages`、`genres`、`song_genres`、`song_languages`、`song_lead_artists`、`song_chorus_artists`、`song_lyricist_artists`、`song_composer_artists` 等。
2. 确保字段存在：如 `songs.language_id`、`songs.chorus_artist_id`、`songs.release_date`、`songs.genre_id`、`songs.film_tv`、`artists.types`、`playlists.sort_order` 等（随版本增量 `ALTER TABLE`）。
3. 将历史 `songs.language_id` / `genre_id` 数据回填到 `song_languages` / `song_genres`（若表已存在）。
4. 初始化默认语言；将仅有 `artist_id` / `chorus_artist_id` 的旧数据补写进多对多关联表（若缺行）。
5. 对 `song_files` 等使用 `_schema_migrations` 记录的一次性结构迁移（如去除全局 hash 唯一等）按名称幂等执行。

## 9. 安全与性能

### 9.1 安全

- 仅允许访问已入库的 song_file_id
- 不暴露真实本地路径
- 下载/播放接口通过后端代理，避免跨域问题
- 预签名 URL 短时有效

### 9.2 性能

- 表字段已建常用索引（`title`、`artist_id`、`album_id`、`format`、`language_id` 等，见模型 `index=True`）
- 歌曲列表使用 `offset`/`limit`；导入时避免单请求过长事务（逐文件提交为主）
- 大库建议：控制单次批量下载数量、反向代理超时与 body 大小
