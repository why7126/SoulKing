# admin-bulk-export Specification

## Purpose

定义「管理端批量导出音频」能力：通过专用接口按所选曲目集合与所选音频格式，收集各曲目下实际存在的音频文件，并以 **单文件流式下载** 或 **ZIP 压缩包** 返回。本规范仅描述 **`POST` 批量下载接口** 的服务端行为；管理界面中单首曲目、多格式时使用浏览器跳转至曲目下载路径的行为不在此接口条目中展开，但与批量接口共用相同的打包与命名辅助逻辑。本规范 **不包含** 元数据表格导出、非音频文件导出。

## Requirements

### Requirement: 批量下载请求体

客户端向批量下载接口提交 JSON 请求体，其中 **曲目标识列表** 与 **格式字符串列表** 均至少包含一项（否则在到达业务逻辑前因请求体验证失败而无法处理）。

#### Scenario: 缺少曲目或格式列表

- **GIVEN** 请求体未同时提供非空的曲目标识列表与格式列表（含列表为空或缺字段）
- **WHEN** 客户端提交批量下载请求
- **THEN** 请求在到达文件收集逻辑前失败（请求体验证）

### Requirement: 请求参数去重与顺序

服务端对请求中的曲目标识与格式字符串分别做 **保序去重**（同一值多次出现时保留首次出现顺序），再用于后续收集。

#### Scenario: 重复标识与格式

- **GIVEN** 请求体中曲目标识或格式字符串存在重复项
- **WHEN** 服务端处理批量下载
- **THEN** 收集逻辑按去重后的列表执行，不因重复项叠加多次同一文件

### Requirement: 按曲目与格式收集音频文件

服务端将格式字符串经规范化（去除无实质内容的条目、统一大小写与点前缀等）得到「目标格式集合」。若规范化后集合为空，则视为无任何文件可收集。否则：按 **去重后的曲目标识顺序**，对每一首曲目，再按 **规范化格式集合经字典序排序后的顺序**，在该曲目下的音频文件中查找 **首个** 与目标格式匹配的条目；每找到一条即加入结果列表。一首曲目可对应多条结果（当选择了多种格式且该曲目下均存在对应文件时）。请求中出现的曲目标识若在库中无对应曲目，则该标识不产生任何文件条目（不单独报错）。

#### Scenario: 部分曲目缺少某格式

- **GIVEN** 批量请求包含多首曲目与多种格式，且其中某首曲目缺少某一种所选格式对应的文件
- **WHEN** 服务端执行收集
- **THEN** 该曲目仅贡献其存在的格式对应文件；缺少的格式不产生条目

### Requirement: 无可下载文件时的错误

若收集结果为空（包括：规范化后无任何有效格式；或所选格式在任一曲目上均无匹配文件），则返回 **未找到** 类错误，说明在已选歌曲中未找到所选格式的文件。

#### Scenario: 所选格式均不匹配

- **GIVEN** 库中在指定曲目上不存在任一请求格式的音频文件
- **WHEN** 客户端提交批量下载请求
- **THEN** 返回未找到类错误

### Requirement: 单文件响应

若收集结果 **恰好一条** 音频文件记录，则返回 **单文件下载响应**：从对象存储按文件记录读取音频对象流式输出；响应头中包含附件形式的内容处置信息与合适的媒体类型；文件名基于曲目标题、主展示艺人信息与格式扩展名等规则生成（与同模块单曲文件下载命名规则一致）。若曲目记录缺失或存储对象不可用，则表现为 **未找到** 类错误。

#### Scenario: 收集结果为一条时返回单文件流

- **GIVEN** 收集逻辑最终得到恰好一条音频文件记录，且存储对象可用
- **WHEN** 服务端完成处理
- **THEN** 客户端收到单音频附件流而非 ZIP

### Requirement: 多文件 ZIP 响应

若收集结果 **多于一条** 音频文件记录，则生成 **ZIP** 压缩包下载响应：内容类型为 ZIP；ZIP 文件名包含固定前缀与基于当前上海时区时间生成的时间戳标签（年月日时分秒及亚秒片段）。包内为每个入选文件写入一条条目。

#### Scenario: 多条文件时返回 ZIP

- **GIVEN** 收集逻辑得到至少两条音频文件记录
- **WHEN** 服务端完成处理
- **THEN** 客户端收到 ZIP 附件响应（内容类型为 ZIP）

### Requirement: ZIP 包内文件名分配

ZIP 内每个文件条目使用归档文件名：优先为「曲目标题与安全艺人片段」加扩展名；若归档文件名与已占用名称冲突，则在主文件名侧追加区分片段以避免覆盖。若无法关联到曲目记录，则使用占位形式的归档名并尽量避免同名冲突。

#### Scenario: 名称冲突时追加区分

- **GIVEN** 两条不同的音频文件记录在打包时将生成相同的归档基础文件名
- **WHEN** 服务端写入 ZIP 条目
- **THEN** 按包内排序后较晚处理的那一条使用带额外区分片段的归档文件名（避免与已占用名称冲突）

### Requirement: ZIP 打包时的单项失败容错

在写入 ZIP 的过程中，若某一音频文件从存储读取失败，服务端 **跳过该条目** 并继续尝试写入其余条目；此类失败不以 HTTP 错误形式返回给客户端（错误信息仅体现在服务侧输出）。最终 ZIP 可能 **少于** 收集到的文件条数。

#### Scenario: 存储中部分对象不可用

- **GIVEN** 收集结果含多条文件记录，且其中至少一条在读取存储对象时失败
- **WHEN** 客户端收到 ZIP 响应
- **THEN** HTTP 响应仍可成功返回 ZIP
- **AND** 包内可能缺少对应失败条目的内容（与 Known Gaps 一致）

## Notes

- 管理端界面中：若用户仅选择 **一首** 曲目下载，实现上通常通过浏览器跳转至曲目下载路径而非调用本批量接口；**多首** 曲目且需打包时才会调用本接口。前端区别不在本规范强制约束。
- 判定「单文件」与「ZIP」的唯一依据是 **收集到的音频文件记录条数**，与请求中的曲目标识个数无简单一一对应（例如多首曲目但仅收集到一条文件记录时仍返回单文件流）。
- 请求体中格式列表在去重后仍会再经规范化集合与 **排序后的格式顺序** 参与收集；与用户在界面勾选顺序不一定一致。

## Known Gaps

- **访问控制**：批量下载接口路径位于管理命名空间下，但服务端路由本身 **未** 绑定鉴权依赖；是否仅限管理员访问取决于网关、反向代理或部署约定。
- **ZIP 完整性**：因单项读取失败会静默跳过，客户端收到的 ZIP 可能与「收集列表」条数不一致；调用方不宜仅凭 HTTP 成功推断包内条目齐全。
- **空 ZIP 包**：若收集结果多于一条但在打包阶段 **全部** 无法从存储读取，响应仍为 ZIP 附件，但包内可能无任何音频条目（极端情形）。
- **非法曲目标识**：请求若包含无法解析为整数的曲目标识项，可能在请求解析阶段失败；具体形态依赖 Web 框架约定。
- **资源占用**：ZIP 在服务端组装时使用内存缓冲；大批量、大文件场景下的内存与超时行为未在代码中单独限额。
